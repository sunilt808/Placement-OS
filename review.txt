# REVIEW UPDATE - 24 AUG 2026 (live-incident + hardening round)

## Incident: "backend failing / no new data"
- Root cause chain: (a) uvicorn --reload worker died during edits while the
  parent kept port 8000 -> zombie listener; (b) backend was fully DOWN over
  the weekend, so nothing was tracked Fri 18:44 -> Mon; (c) browser held a
  stale JWT that is now invalid by design.
- Fix: stable start without --reload (logs in backend/logs/), 4-day
  catch-up scan backfilled ~50 messages, watchdog now self-heals the
  "connected but deaf" case after 2x interval.

## Notifications were silently failing
- Telegram API returned `400 chat not found` on EVERY send. Bot token is
  valid (@sunil_placement_bot) but the target chat was never started.
- USER ACTION REQUIRED: open @sunil_placement_bot in Telegram and press
  START once; confirm TELEGRAM_CHAT_ID equals your @userinfobot id.
- Code now prints an explicit hint when this happens + plain-text retry
  fallback for HTML parse errors.

## Company-name quality (user-reported)
- "Thanks & Regards" was extracted as a company for the eInfochips drive;
  camelCase brands (eInfochips) were rejected by the validator entirely.
- Fixed: sign-off/greeting blacklist, Subject-line pattern
  (`Subject: <Company> Campus Drive ...`), lowercase-start rule replaced by
  no-capitals rule. Backfill repaired 14 live drives incl. Salesforce,
  HCLTech, SAP, Infrrd, eInfochips. Rerun anytime:
  python scripts/backfill_companies.py

## Verification state
- Backend test suite: 28/28 PASS (adds company-artifact e2e, endpoint auth,
  docs-hiding, extractor regressions). Frontend builds clean.
- Live server: health OK, userbot connected, Swagger/OpenAPI return 404.

## Answers to open questions
- Live PDF tracking: YES - userbot routes documents/photos/spreadsheets in
  real time AND history scans cover downtime windows.
- "Not CSE" badge: was driven by weak-score boolean; now only explicit
  non-CSE evidence shows Not CSE, otherwise Unclassified (recall first).

# REVIEW UPDATE - 24 AUG 2026, ROUND 2 (notification stack + UI + deploy prep)

## Root cause found for ALL "Gemini enable fails" reports (multi-layer)
1. Frontend client.js defaulted to port 8001 while server ran on 8000.
2. GeminiPage called /gemini/* WITHOUT the /api prefix -> guaranteed 404
   even on the right port. Same latent bug fixed in Opportunities.jsx
   bulk-delete (/storage/* -> /api/storage/*).
3. A stale orphaned uvicorn on 8001 was ALSO double-polling getUpdates
   (the Telegram Conflict spam). Killed; main.py shutdown now uses
   asyncio.wait_for timeouts so reload workers can't linger again.
4. ai_service required GEMINI_ENABLED=true which was never in .env ->
   "[AI] Gemini unavailable" forever. Now initializes on key presence.

## Auto-notification hardening
- LIVE TEST revealed the real reason no alerts ever arrived:
  Telegram returns `400 chat not found` — bot was never STARTed.
  USER ACTION STILL REQUIRED: open the bot, press START once.
- Startup ping added (main.py): sends "PlacementOS is online" on boot;
  failure prints the exact remedy. Flag: STARTUP_PING=true.
- Pipeline alert path now logs success per drive and prints a remedy
  hint on failure. Flag: AUTO_NOTIFY_NEW_OPPORTUNITY=true.
- Gemini chat quota exhaustion now returns clean HTTP 429 with friendly
  text; frontend renders it as a chat bubble, not an error dump.

## Frontend notification layer
- NEW Topbar.jsx: top navbar with bell + unread badge, dropdown panel
  aggregating new drives (<24h), urgent deadlines, pending reminders;

  60s polling. Fixed button UA font-color inheritance (dark-on-dark).
- Dashboard/Opportunities detect new arrivals on poll and toast them.
- GeminiPage toggle rewritten: busy states, optimistic status flip,
  toast errors with real reasons (backend unreachable / session expired).

## UI additions
